커피챗 추천 엔진 설계 문서

데이터가 적은 지금부터, 진단·활동·전공·학교·고민 등 신호가 폭증할 미래까지 — 같은 엔진이 그대로 확장되도록 설계한다.

대상 개발 · 기획 상태 Draft v1 범위 커피챗 코치 추천/노출 원칙 적합도 · 공정 · 투명
TL;DR

지금 엔진을 만들지 마라. 대신 연료를 모아라.

  1. 복잡한 추천 엔진은 지금 불필요 — 데이터가 없으면 개인화할 재료가 없다(콜드스타트). 지금은 단순·투명한 규칙 정렬로 충분.
  2. 지금 해야 할 단 하나는 “이벤트 로깅” — 엔진은 나중에 만들어도 되지만, 학습 연료(로그)는 지금 안 쌓으면 영원히 사라진다.
  3. 엔진은 “플러그형 신호 × 3단 파이프라인”으로 설계 — 신호를 함수 단위로 꽂는 구조라, 데이터가 늘 때 feature만 추가하면 복잡도가 폭발하지 않는다.
01 — PRINCIPLES

설계 원칙

모든 추천/노출 결정은 아래 5가지를 통과해야 한다. 알고리즘보다 원칙이 먼저다.

① 적합도 우선
인기·유명세가 아니라 “내 질문에 맞는가”. 매칭 점수가 랭킹의 주축.
② 공정 노출
신규·저노출 코치에 가산점(exploration). 특정 코치 독식 방지 = 코치 명예 원칙.
③ 투명성
“왜 추천됐는지”(비전공·홍익대·빠른응답 등)를 한 줄로 노출.
④ 중복 회피
이미 본 코치는 감점. 같은 코치·같은 블록 반복 금지.
⑤ 검증 게이트
헬로마이미 검증 통과 코치만 후보. 신뢰가 노출의 전제.
02 — ARCHITECTURE

3단 파이프라인

하나의 거대 알고리즘 ❌ → 레이어로 쪼갠다 ⭕. 각 단계는 독립적으로 교체·개선 가능.

1
후보 생성 · Retrieval
필터·고민·직무·회사로 전체 코치를 수백 명 후보로 좁힌다. 싸고 빠르게. 검증 안 된 코치·범위 밖은 여기서 제외.
2
스코어링 · Ranking
후보마다 score = Σ(신호값 × 가중치). 각 신호는 독립 함수. 여기가 “엔진”의 심장이자 확장 지점.
3
재정렬 · Re-rank
비즈니스 규칙 적용 — 본 것 제외 · 같은 코치 반복 방지 · 신규 코치 가산 · 다양성 보정.
4
블렌딩 · Blending
최종 피드 조립 — 코치 카드 + 추천 블록(빠른/도움/비전공/외국계/같은학교) + 요청 카드를 규칙대로 인터리빙.
03 — SCORING

플러그형 신호 (Feature)

신호 하나 = 순수 함수 하나. 0~1 값과 가중치를 반환한다. 데이터 없는 신호는 중립 처리 후 가중치 재정규화 → 같은 엔진이 Day 1부터 성숙기까지 동작.

// 신호 = (학생, 코치) → { value: 0~1, weight }
const FEATURES = [
  jobMatch,        // 관심 직무 ↔ 코치 직무
  companyMatch,    // 가고싶은 회사유형 ↔ 코치
  concernMatch,    // 고민 태그 ↔ 코치 추천대상
  coachQuality,    // 도움% · 응답시간 · 질문수
  freshness,       // 최근 활동/신규
  fairnessBoost,   // 저노출 코치 가산 (exploration)
  // ↓ 데이터 생기면 그냥 추가
  majorMatch, schoolMatch, faceDiagnosis, activityAffinity, purchaseHistory,
];

function score(student, coach, ctx){
  let sum = 0, wsum = 0;
  for (const f of FEATURES){
    const r = f(student, coach, ctx);
    if (r == null) continue;   // 데이터 없음 → 스킵(재정규화)
    sum  += r.value * r.weight;
    wsum += r.weight;
  }
  return wsum ? sum / wsum : 0.5;   // 신호 없으면 중립
}
  • 가중치는 처음엔 손으로 튜닝 → 로그가 쌓이면 학습으로 전환(Phase 4).
  • 신호 추가 = 배열에 함수 하나 push. 엔진 재작성 없음.
  • “왜 추천?”은 가장 크게 기여한 feature 이름으로 자동 생성(투명성 원칙).
04 — SIGNAL TIERS

신호를 “데이터 준비도”로 계층화

아래 티어부터 하나씩 “켠다”. 위 티어는 데이터가 생기는 순간 feature만 꽂으면 된다.

티어신호데이터 출처언제
T0고민·직무·회사 매칭 · 코치 품질(도움%·응답) · 신규 공정성 · 최신성코치 프로필 · 명시적 선택즉시
T1전공 · 학교(동문) · 학년 · 고민 태그온보딩 1회 입력곧
T2활동(클릭·체류·질문) · 커피콩 구매 이력 · 검색어이벤트 로그로그 축적 후
T3FACE 진단 · 안녕하루 데이터 · 수강 과목크로스 프로덕트 연동연동 시
T4협업 필터링 · 학습된 가중치 · 임베딩 유사도충분한 상호작용성숙기

‘엄청 복잡한 알고리즘’은 이 표를 한꺼번에 구현할 때 생긴다. 티어별로 나눠 켜면 각 단계는 단순하다.

05 — COLD START

데이터가 없을 때 (지금)

  • 학생 신호 없음 → 온보딩 1문항(관심 직무/고민)만 받아 T0·T1으로 시작. 나머지 feature는 중립.
  • 신규 코치 → 후기·지표가 없으니 품질 점수 대신 공정 노출 가산으로 초기 기회 부여(exploration).
  • 노출 다양성 → 초반엔 정확도보다 “다양하게 보여주고 반응을 학습”. 클릭·질문이 곧 T2 데이터가 된다.
  • 정직한 한계 → 코치 풀이 얇으면 무한 스크롤 대신 “현재 N명” 페이지네이션이 더 정직하다.
06 — ROADMAP

단계별 도입

NOW
Phase 0 · 규칙 정렬 + 이벤트 로깅
T0 규칙으로 랜덤 대체. 로깅 스키마 확정이 진짜 과업.
NEXT
Phase 1 · 온보딩 프로필
전공·학교·고민 입력 → T1 매칭 켜기. 동문/전공 추천 시작.
+
Phase 2 · 행동 기반
로그 축적 → T2(활동·구매) 켜기. “본 것 제외”·관심 추론.
+
Phase 3 · 크로스 프로덕트
FACE·안녕하루·수강 연동 → T3. 진단 결과로 방향 추천.
LATER
Phase 4 · 학습 랭킹
상호작용 충분 → T4. 가중치 학습·협업필터링·A/B로 최적화.
07 — EVENT LOGGING

지금 확정할 로깅 스키마

미래 엔진의 훈련 데이터. 지금 안 쌓으면 복구 불가. 이것이 Phase 0의 핵심 산출물.

이벤트언제핵심 필드
impression카드가 화면에 노출coach_id, position, source(feed/reco/search)
click카드 탭 → 상세coach_id, dwell_ms
search검색·필터 실행query, scope, facets, result_count
request“○○ 찾아주세요” 요청company/job, 미충족 수요 신호
question_sent커피콩으로 질문 전달coach_id, question_text, 상황(학년·전공)
answer_helpful도움 평가coach_id, verdict, 강점태그
review후기 작성coach_id, tags, text

공통 필드: student_id · coach_id · context · timestamp. request 이벤트는 특히 값지다 — 어떤 현직자를 영입해야 하는지 수요 신호가 된다(코치 리크루팅 우선순위).

08 — GOVERNANCE

엔진에 박을 값

코치 명예
점수 줄세우기·“인기 1위” 금지. 공정 노출로 독식 방지.
프라이버시
진단·활동·구매 데이터는 최소 수집·동의 기반. 추천 목적 외 사용 금지.
설명 가능성
모든 추천에 사유 1줄. 블랙박스 랭킹 지양.
피드백 루프 감시
인기 코치가 더 노출→더 인기 되는 편향 모니터링·보정.
▶ 지금 할 일 (Phase 0)

엔진 말고, 이 두 가지

복잡한 추천 엔진은 데이터가 쌓인 뒤다. 지금 확정할 것은 딱 둘.

1. T0 규칙 정렬로 교체 — 적합도(고민·직무 매칭) + 품질 + 신규 공정성 + 최신성
2. 이벤트 로깅 스키마 확정 — impression·click·question·helpful·request … (미래 학습 연료)
