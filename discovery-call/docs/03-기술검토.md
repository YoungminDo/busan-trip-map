기준: PRD v1 / 전략 기획안 v2.5 / 검토일 2026-07-12

## 이 세션에서 검증 불가능한 것 (Week 1–2 실기기 스파이크로 이월)

1. **CallKit E2E**: VoIP 인증서 발급 → 실제 아이폰에서 잠금화면 수신 → 수락 → LiveKit 룸 연결까지의 전체 체인 (시뮬레이터로는 PushKit 테스트 불가)
2. **지연 실측**: 한국 네트워크에서 유저 발화 종료 → AI 첫 음성까지 1.5초 이내 여부
3. **STT/TTS 한국어 실품질**: WoZ 블라인드로만 판정 가능
4. **iOS 심사 통과**: TestFlight 제출 전 판단 불가

## 이 세션에서 코드로 검증한 것 (server-core)

PRD의 비즈니스 규칙을 외부 API 없이 순수 로직으로 구현하고 테스트로 고정했다 — 벤더가 바뀌어도 이 규칙들은 그대로 간다:

- **스케줄러 정책**: 무료 주 5회 쿼터 / 재시도 1회 / 스누즈 3옵션 무페널티 / 시험기간 모드(주 2회) / 월 분수 하드캡 킬스위치
- **대화 엔진 골격**: 체크인→메인(질문 로테이션, 콜백 우선)→반영→연착륙 랩업 상태머신, 침묵 정책
- **페르소나 시스템**: 3종 톤 레이어 + 공유 코어 정책, 위기 시 페르소나 무시 오버라이드
- **위기 프로토콜**: 어휘 사전 이중 게이트(LLM 단독 판정 금지 구조), 심각도별 대응
- **미러링 계약**: 직접 인용 필수 검증 + 성격어휘 필터(대화 10회 미만 차단) — 바넘 게이트의 코드 레벨 구현
- **관측 파이프라인**: candidate→emerging→established 승격, 모순 시 superseded, 삭제 시 파생 관측 제거
- **원가 미터**: 분당 원가 집계, 유저별 월 분수, self-host 트리거(월 API 100만 원) 알림

## 결론

스택 변경 없이 진행 가능. 조건부 항목(3·4·6)은 전부 WoZ와 Week 1–2 스파이크에서 판정하도록 이미 일정에 반영되어 있다. 가장 큰 잔여 리스크는 기술이 아니라 **Apple 심사(5번)와 실기기 E2E(1번)** — 그래서 10주 계획의 첫 2주가 이 둘의 스파이크다.

## 추가 검토 (v2.6): 헬로마이미 앱 탑재 전제

창업자 결정 — 이 기능은 추후 헬로마이미 앱에 탑재된다. 아키텍처에 미치는 영향:

| 레이어 | 설계 원칙 | 현재 상태 |
|---|---|---|
| 서버 | **앱 무관 독립 API 서비스** — 어떤 클라이언트든 붙는다. 계정은 자체 회원이 아니라 외부 user_id 매핑(헬로마이미 계정 연동 대비). 인증은 JWT 위임 방식 | ✅ 서버 코어는 이미 앱 비의존. API 레이어 설계 시 user_id를 외부 키로 유지 |
| 클라이언트 | 통화 기능 전체(수신·통화중·요약카드)를 **자체 패키지로 격리** — 호스트 앱의 코드·상태에 의존하지 않는 경계 유지. 진입점은 "통화 탭/버튼 하나"로 좁게 | ⚠️ 스캐폴드 단계라 비용 낮음. 이식 방식은 헬로마이미 스택에 따라 갈림: Flutter면 feature 패키지 그대로, 네이티브(iOS)면 Flutter add-to-app 모듈 또는 화면 네이티브 재작성(서버·대화엔진은 공유), RN이면 네이티브 브릿지 경유 |
| 데이터 | 일기·관측·프로필 스키마를 **헬로마이미의 다른 기능이 소비 가능한 계약**으로 유지 (예: 프로필을 헬로마이미 기존 기능에 노출) | ✅ domain.py 스키마가 이미 독립적 |
| 결제 | 구독을 자체 앱 IAP로 만들면 헬로마이미 탑재 시 구독 이전 문제 발생 → **서버측 엔타이틀먼트(권한) 관리**로 설계, IAP는 껍데기 | 설계에 반영 필요 (Week 10) |
| 심사 | VoIP push 사용례 소명을 헬로마이미 제출 시에도 반복해야 함 — 소명 노트를 재사용 가능한 문서로 유지 | 메모 |

**미확정 — 창업자 확인 필요**: ① 헬로마이미의 기술 스택 ② 헬로마이미의 현재 유저 규모·구성(대학생 비중 — WoZ 모집과 초기 배포 채널이 될 수 있는지) ③ 검증을 독립 앱으로 할지 처음부터 헬로마이미 내 기능으로 할지.

## 추가 검토 (v2.7): 헬로마이미 실사 결과 — 클라이언트 방향 변경

`youngmindo/hello-my-me` 레포 직접 검토 결과 (2026-07-12):

**헬로마이미(DA-SH UNIV)의 실체**
- **스택**: Next.js 16 (TypeScript, Tailwind v4) + **Capacitor 8** 하이브리드 앱(iOS/Android 셸이 `hmm.da-sh.io` 웹을 원격 로드) + Supabase(DB·계정) + 카카오 OAuth(id.da-sh.io 게이트웨이) + Vercel + FCM 푸시 + Toss 웹결제 & cordova IAP
- **제품**: 대학생 커리어 플랫폼 — READ 진단, 자소서(cover-letter), 상담(counseling), 프로그램, 커뮤니티 등 라우트 49개
- **배포 채널**: 대학 취업정보센터·총학생회 B2G (재학생 전체 이메일·문자 채널)

**이 발견이 바꾸는 것 3가지**

1. **클라이언트를 Flutter → Next.js(React) + Capacitor로 변경한다.**
   타겟(대학생)과 호스트 스택이 확인된 이상, Flutter 독립앱은 "나중에 React로 전부 재작성"을 예약하는 선택이다. 통화 기능의 UI(온보딩·홈·요약카드·주간요약)는 헬로마이미 안의 라우트(`/call/*`)로 만들고, 네이티브가 필수인 부분(PushKit VoIP 수신 → CallKit 표시, 오디오 세션)만 Capacitor 플러그인으로 얹는다. `app_flutter/` 스캐폴드는 폐기(deprecated) 표시.
   - 통화 오디오: livekit-client(JS SDK)가 WKWebView에서 동작(getUserMedia iOS 14.3+). 품질 미달 시 네이티브 LiveKit Swift SDK를 플러그인 경유로 승격 — **Week 1–2 스파이크 재정의: "Capacitor CallKit E2E + WebView 통화 품질"**
   - 리스크: Capacitor용 CallKit/VoIP 플러그인(capacitor-plugin-callkit-voip 등)은 flutter_callkit_incoming만큼 성숙하지 않음 — 스파이크 최우선 검증 항목. 필요 시 자체 경량 플러그인 작성(PushKit+CallKit 브릿지는 코드량이 크지 않다).

2. **백엔드는 그대로 유효, DB는 Supabase로 통합 가능.**
   Python 서버 코어(스케줄러·바넘 게이트·위기 프로토콜·파이프라인)와 LiveKit Agents는 클라이언트 무관 — 변경 없음. DB는 우리 설계(Postgres+pgvector)가 Supabase(=Postgres, pgvector 지원)와 일치하므로 **헬로마이미의 Supabase를 공유**하고, 계정도 기존 카카오 OAuth user_id를 그대로 쓴다. 별도 회원 체계·계정 매핑 작업이 통째로 사라진다.

3. **검증 경로: 독립 앱이 아니라 헬로마이미 내 기능으로.**
   - 타겟 일치(대학생 커리어), 배포 채널 보유(대학 B2G — WoZ 모집도 이 채널로), 자소서·진단 기능과의 시너지(통화로 쌓인 프로필 → cover-letter 재료)까지 3박자가 맞는다.
   - 원격 로드 구조의 이점: **통화 UI·일기·주간요약은 웹 배포만으로 즉시 업데이트**(앱 심사 없음). 앱 심사가 필요한 건 네이티브 플러그인(CallKit) 추가 시 1회.
   - 유의: 웹 원격 로드 + IAP 구조에 VoIP push를 얹으면 심사 심의가 까다로울 수 있음 — 실통화 데모 영상 소명 필수(기존 판정 5번과 동일).

**수정된 스파이크 (Week 1–2)**: ① 헬로마이미 iOS 셸에 PushKit+CallKit 플러그인 얹어 수신 E2E ② WKWebView에서 livekit-client 통화 품질·지연 실측 ③ 미달 시 네이티브 오디오 경로 판단.

**남은 확인 사항**: 헬로마이미의 현재 가입자 규모(WoZ 모집 모수), 통화 기능의 브랜드 위치(독립 서브브랜드 vs '헬로마이미 통화').
